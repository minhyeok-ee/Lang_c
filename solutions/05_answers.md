## A. C 언어 키워드

### 1. volatile
컴파일러에게 "이 변수는 **코드 밖에서 언제든 바뀔 수 있으니** 최적화로 값을 캐시하지 말고 매번 메모리에서 읽어라"라고 알려준다.
꼭 필요한 경우:
1. **메모리 매핑된 하드웨어 레지스터** (상태 레지스터 값은 하드웨어가 바꾼다)
2. **ISR과 메인 코드가 공유하는 전역 변수**
3. **멀티스레드(RTOS 태스크)가 공유하는 변수**

예: `while (!flag);`에서 flag가 ISR에서 바뀌는데 volatile이 없으면 컴파일러가 무한 루프로 최적화할 수 있다.
주의: volatile은 **원자성(atomicity)을 보장하지 않는다.** 동시 접근 보호는 따로 해야 한다.

### 2. static
- (a) 함수 안 지역 변수: 수명이 프로그램 전체로 늘어나 **호출 사이에 값이 유지**된다. 초기화는 한 번만 된다.
- (b) 파일 범위 전역 변수: **다른 파일에서 접근할 수 없게**(internal linkage) 숨긴다.
- (c) 함수: 그 함수를 **해당 파일 안에서만** 호출할 수 있게 한다.

(b), (c)는 모듈 캡슐화와 이름 충돌 방지에 쓰인다.

### 3. const 포인터
`*`를 기준으로 **왼쪽의 const는 가리키는 값**, **오른쪽의 const는 포인터 자체**를 고정한다.
- `const int *p1`, `int const *p2`: 같은 의미. 가리키는 **값 변경 불가**, 포인터는 다른 곳을 가리킬 수 있음
- `int *const p3`: 포인터 **주소 변경 불가**, 값은 변경 가능 (선언 시 초기화 필요)
- `const int *const p4`: 둘 다 변경 불가

### 4. const volatile
가능하다. **읽기 전용 하드웨어 상태 레지스터**가 대표적인 예다.
```c
#define STATUS_REG (*(const volatile uint32_t *)0x40001000)
```
- const: 우리 코드가 쓰면 안 된다
- volatile: 하드웨어가 값을 바꾸므로 매번 읽어야 한다

### 5. extern
"이 변수/함수는 **다른 곳에 정의되어 있다**"는 선언이다. 메모리를 할당하지 않는다.
헤더에 `int g = 0;`처럼 **정의**를 넣고 여러 .c 파일에서 include하면, 각 파일마다 g가 정의되어 **링크 에러(multiple definition)**가 난다.
올바른 방법: 헤더에는 `extern int g;`(선언), .c 파일 하나에만 `int g = 0;`(정의)

### 6. #define vs const vs inline
| | `#define` | `const` 변수 | `static inline` 함수 |
|---|---|---|---|
| 처리 시점 | 전처리기의 텍스트 치환 | 컴파일러 | 컴파일러 |
| 타입 검사 | 없음 | 있음 | 있음 |
| 디버거에서 보임 | X | O | O |
| 부작용 문제 | 인자가 여러 번 평가될 수 있음 | - | 인자 한 번만 평가 |
| 메모리 | 사용 안 함 | 사용할 수 있음 | 인라인되면 호출 비용 없음 |

`#define`은 조건부 컴파일(`#ifdef`), 헤더 가드, 레지스터 주소 등에 여전히 필요하다.

## B. 메모리

### 7. 메모리 영역
- **text(code)**: 실행 코드, 문자열 리터럴·const 전역 같은 읽기 전용 데이터(rodata). 보통 Flash에 위치
- **data**: 0이 아닌 값으로 초기화된 전역/static 변수. 초기값은 Flash에 있고 부팅 시 RAM으로 복사
- **bss**: 초기화되지 않았거나 0으로 초기화된 전역/static 변수. 부팅 시 0으로 채움
- **heap**: malloc으로 동적 할당한 메모리
- **stack**: 지역 변수, 함수 매개변수, 리턴 주소

| 변수 | 위치 |
|---|---|
| `int a = 10;` | data |
| `int b;` | bss |
| `static int c;` | bss |
| `msg` 포인터 변수 | data (초기값이 주소이므로) |
| `"hello"` 문자열 자체 | text(rodata) |
| `int d;` | stack |
| `static int e = 1;` | data |
| `h` 포인터 변수 | stack |
| `h`가 가리키는 4바이트 | heap |

### 8. 임베디드에서 malloc을 피하는 이유
1. **메모리 단편화**: 오랫동안 할당/해제를 반복하면 전체 여유 공간은 있어도 연속 공간이 없어 실패한다. 24시간 켜두는 모니터에 치명적
2. **실행 시간이 일정하지 않음**: 실시간성을 보장하기 어렵다
3. **실패 처리 어려움**: 런타임에 할당이 실패하면 복구하기 힘들다
4. RAM이 작다

대안: 정적 배열, 고정 크기 메모리 풀, 부팅 시 한 번만 할당

### 9. 스택 오버플로
원인: 깊은 재귀, 큰 지역 배열, ISR 중첩, 태스크 스택 크기를 너무 작게 설정
탐지 방법:
- **스택 페인팅**: 부팅 시 스택을 0xDEADBEEF 같은 패턴으로 채워두고, 나중에 덮어써지지 않은 영역을 확인해 최대 사용량(high water mark)을 측정
- 스택 끝에 **카나리(canary)** 값을 두고 주기적으로 검사
- MPU(메모리 보호 장치)로 스택 경계 접근 시 예외 발생
- RTOS의 스택 오버플로 검사 기능 사용

### 10. 메모리 버그
- **메모리 누수**: 할당한 메모리를 해제하지 않아 사용 가능한 메모리가 점점 줄어듦
- **댕글링 포인터**: 이미 해제되었거나 범위를 벗어난 메모리(예: 함수의 지역 변수 주소를 반환)를 가리키는 포인터
- **버퍼 오버플로**: 배열 크기를 넘어서 써서 인접 메모리(다른 변수, 리턴 주소)를 덮어씀. `strcpy` 대신 길이를 확인하는 함수를 쓰고 경계를 검사해야 함

### 11. 엔디안
- 빅 엔디안: 큰 자리 바이트를 낮은 주소에 저장 (0x12345678 → 12 34 56 78)
- 리틀 엔디안: 작은 자리 바이트를 낮은 주소에 저장 (→ 78 56 34 12). x86, 대부분의 ARM

통신에서는 **보내는 쪽과 받는 쪽의 엔디안이 다를 수 있어서** 프로토콜에 바이트 순서를 명시한다. 네트워크는 빅 엔디안이다.
구조체를 `memcpy`로 통째로 보내면 엔디안과 패딩 문제가 모두 생기므로 바이트 단위로 직렬화하는 것이 안전하다.
(EDID도 제조사 ID는 빅 엔디안, 제품 코드는 리틀 엔디안이다)

## C. 인터럽트와 동시성

### 12. ISR 작성 시 주의점
1. **최대한 짧고 빠르게**: 플래그 설정이나 버퍼 저장만 하고, 긴 처리는 메인 루프에서
2. **블로킹 함수 금지**: delay, printf, malloc, 뮤텍스 대기 등
3. 공유 변수는 **volatile**로 선언하고 메인 쪽에서 **임계 구역 보호**
4. **인터럽트 플래그 클리어**: 안 하면 ISR이 계속 다시 호출됨
5. 스택 사용 최소화 (큰 지역 변수 피하기)
6. 부동소수점 연산 피하기 (FPU 레지스터 저장 비용)
7. **재진입(reentrant)** 가능한 함수만 호출

### 13. ISR에서 printf/malloc 금지 이유
- **재진입 불가**: 메인 코드가 printf나 malloc 실행 중에 인터럽트가 걸려 ISR에서 같은 함수를 호출하면 내부 상태(버퍼, 힙 리스트)가 깨진다
- **시간이 오래 걸림**: printf는 UART 전송을 기다리느라 수 ms가 걸릴 수 있어 다른 인터럽트를 놓친다
- 내부적으로 락을 쓰면 **데드락** 발생 가능

### 14. 폴링 vs 인터럽트
| | 폴링 | 인터럽트 |
|---|---|---|
| 방식 | 주기적으로 상태를 확인 | 이벤트 발생 시 CPU에 알림 |
| 장점 | 구조가 단순, 예측 가능, 동시성 문제 적음 | 빠른 응답, 대기 중 CPU 낭비 없음(저전력) |
| 단점 | CPU 낭비, 확인 주기 사이의 이벤트 지연/누락 | 동시성 문제, 디버깅이 어려움, 인터럽트가 너무 잦으면 오버헤드 |
| 적합 | 느리고 주기적인 입력(버튼, 온도) | 빠르고 불규칙한 이벤트(UART 수신, 신호 감지) |

### 15. 경쟁 조건
두 실행 흐름이 공유 자원에 동시에 접근해서 **실행 순서에 따라 결과가 달라지는 문제**.
예: 메인에서 `count++`는 읽기-더하기-쓰기 3단계인데, 중간에 ISR이 count를 바꾸면 그 변경이 사라진다.
해결 방법:
- 메인 쪽 접근 구간에서 **인터럽트를 잠깐 비활성화** (임계 구역을 최대한 짧게)
- 원자적(atomic) 연산 사용
- **단일 생산자/단일 소비자 링 버퍼**: head는 ISR만, tail은 메인만 수정
- RTOS에서는 뮤텍스, 세마포어, 큐 사용

### 16. 뮤텍스 vs 세마포어, 우선순위 역전
- **뮤텍스**: 공유 자원에 대한 **상호 배제**용 잠금. **잠근 태스크만 풀 수 있다**(소유권). 우선순위 상속 지원
- **세마포어**: 카운터 기반. **이벤트 신호 전달**(바이너리)이나 **개수가 제한된 자원 관리**(카운팅)에 사용. 소유권 없음, ISR에서 give 가능

**우선순위 역전**: 낮은 우선순위 L이 뮤텍스를 잡고 있는 동안 높은 우선순위 H가 그 뮤텍스를 기다린다. 이때 중간 우선순위 M이 L을 선점하면, H가 M보다 우선순위가 높은데도 M이 끝날 때까지 기다리게 된다.
해결: **우선순위 상속**(L이 잠시 H의 우선순위를 물려받음), 우선순위 상한 프로토콜

### 17. 워치독
소프트웨어가 멈추거나(무한 루프, 데드락) 폭주하면 **자동으로 시스템을 리셋**하는 하드웨어 타이머.
정상 동작 중에는 주기적으로 타이머를 리셋(kick/feed)한다.
올바른 위치: **메인 루프에서 모든 핵심 작업이 정상적으로 한 바퀴 돌았을 때** kick한다.
- ISR에서 kick하면 안 된다: 메인 루프가 멈춰도 타이머 인터럽트는 계속 돌아서 리셋이 안 됨
- 여러 태스크가 있으면 각 태스크가 "살아있음" 플래그를 세우고, 모든 플래그가 확인됐을 때만 kick

## D. 통신과 하드웨어

### 18. UART vs I2C vs SPI
| | UART | I2C | SPI |
|---|---|---|---|
| 신호선 | TX, RX (2) | SDA, SCL (2) | SCLK, MOSI, MISO, CS (4 + 장치마다 CS) |
| 동기 방식 | 비동기 (보드레이트를 미리 맞춤) | 동기 (클럭 공유) | 동기 |
| 속도 | 보통 ~115200bps (더 빠를 수 있음) | 100kbps / 400kbps / 3.4Mbps | 수 Mbps ~ 수십 Mbps |
| 통신 | 1:1, 전이중 | 다중 마스터/다중 슬레이브, 7비트 주소 | 1 마스터 : 다중 슬레이브, 전이중 |
| 장점 | 간단, 긴 거리(RS-232/485) | 선 2개로 여러 장치 연결 | 가장 빠름, 구조 단순 |
| 단점 | 클럭 오차에 민감 | 느림, 버스 정지(stuck) 가능 | 선이 많음 |
| 모니터 예시 | 디버그 콘솔, 외부 제어(RS-232) | EDID/DDC, 터치/센서 IC | SPI 플래시(펌웨어 저장) |

### 19. I2C 풀업, ACK, clock stretching
- **풀업 저항**: I2C 장치는 오픈 드레인 출력이라 라인을 **LOW로 당기기만** 할 수 있다. HIGH는 풀업 저항이 만든다. 여러 장치가 동시에 구동해도 단락이 나지 않는 구조다. 저항이 너무 크면 상승 시간이 느려지고, 너무 작으면 전류가 커진다.
- **ACK/NACK**: 매 바이트(8비트) 전송 후 9번째 클럭에서 수신 측이 SDA를 LOW로 당기면 ACK(받았음), HIGH로 두면 NACK(주소 없음, 수신 불가, 또는 마지막 바이트).
- **Clock stretching**: 슬레이브가 처리할 시간이 필요할 때 **SCL을 LOW로 붙잡아** 마스터를 기다리게 하는 것.

### 20. I2C 통신 불량 분석 순서
1. **하드웨어**: 전원 인가 여부, 풀업 저항 유무와 값, 배선/납땜, GND 공통 연결
2. **오실로스코프**: 신호 전압 레벨(3.3V/5V 호환), 상승 시간, 노이즈
3. **로직 분석기**: START 조건, 슬레이브 주소, ACK 응답 여부 확인
4. **주소 확인**: 7비트/8비트 주소 표기 혼동(0x50 vs 0xA0), 주소 핀 설정. 버스 스캔으로 응답하는 주소 찾기
5. **설정**: 클럭 속도가 장치 지원 범위인지, 핀 모드(오픈 드레인, 대체 기능) 설정
6. **데이터시트**: 레지스터 접근 순서(repeated start 필요 여부), 장치 초기화 시간
7. **버스 멈춤**: SDA가 LOW로 고정됐으면 SCL을 9번 토글해 버스 복구

### 21. PWM
일정한 주기에서 **HIGH 구간의 비율(duty cycle)**을 바꿔 평균 전력을 조절하는 방식.
백라이트 LED는 주파수가 충분히 높으면 사람 눈이 깜빡임을 느끼지 못하고, duty 비율에 비례한 평균 밝기로 인식한다.
- 주파수가 낮으면 플리커가 발생해 눈의 피로를 유발 → 플리커 프리 모니터는 높은 주파수 PWM이나 DC 디밍 사용
- 주파수가 가청 대역이면 코일에서 소음이 날 수 있음

### 22. 오픈 드레인 vs 푸시풀
- **푸시풀**: 트랜지스터 2개로 HIGH와 LOW를 모두 능동적으로 구동. 빠르고 강하지만, 두 출력을 연결하면 단락 위험
- **오픈 드레인**: LOW만 구동하고 HIGH는 끊어진(high-Z) 상태. **외부 풀업 필요**. 여러 장치를 한 선에 연결 가능(wired-AND), 다른 전압 레벨과 연결 가능. I2C, 인터럽트 라인에 사용

## E. 디스플레이 장치

### 23. EDID
**Extended Display Identification Data**. 모니터가 자신의 정보(제조사, 모델, 지원 해상도와 타이밍, 선호 해상도, 화면 크기 등)를 소스 기기(PC, 게임기)에 알려주는 데이터 구조다.
- 기본 블록 128바이트 + 확장 블록(CTA-861: HDMI 오디오, HDR 정보 등)
- 모니터의 EEPROM 또는 스케일러 내부 메모리에 저장
- 영상 케이블의 **DDC 채널(I2C 기반)**을 통해 소스가 읽어간다. 주소는 0x50(7비트)
- 헤더 `00 FF FF FF FF FF FF 00`과 마지막 바이트 체크섬으로 유효성 확인

### 24. HDMI 연결 후 화면이 나오기까지
1. 모니터 전원 ON → MCU/스케일러 부팅, 설정값(밝기, 입력 소스) 로드
2. 케이블 연결 → 소스가 **+5V**를 공급, 모니터는 준비되면 **HPD(Hot Plug Detect)**를 HIGH로 올림
3. 소스가 DDC(I2C)로 **EDID를 읽음**
4. 소스가 EDID를 보고 **출력 해상도와 타이밍을 결정**
5. (보호 콘텐츠라면) **HDCP 인증**
6. TMDS/FRL 신호 전송 시작
7. 스케일러가 **신호를 감지하고 타이밍을 측정**(해상도, 주사율), 안정화될 때까지 대기
8. 스케일러가 패널 해상도에 맞게 **스케일링과 화질 처리**, OSD 합성
9. **패널 전원 시퀀스**: 패널 전원 ON → 영상 신호(LVDS/eDP/V-by-One) 출력 → **백라이트 ON**

신호가 없으면 "No Signal" OSD를 띄우고 일정 시간 후 절전 모드로 들어간다.

### 25. 패널 전원 시퀀스
- **켤 때**: 패널 로직 전원(VCC) → 영상 신호 → **마지막에 백라이트**
- **끌 때**: **백라이트 먼저 OFF** → 영상 신호 OFF → 패널 전원 OFF

이유:
- 신호가 안정되기 전에 백라이트가 켜지면 **쓰레기 화면, 노이즈, 번쩍임**이 사용자에게 보인다
- 전원 없이 신호를 넣거나 순서가 어긋나면 **패널 드라이버 IC 손상(래치업)**이나 수명 저하가 생길 수 있다
- 패널 데이터시트에 각 단계 사이의 **최소/최대 지연 시간(T1, T2, ...)**이 정의되어 있고 펌웨어가 이를 지켜야 한다

### 26. 스케일러 IC
모니터의 **메인 영상 처리 SoC**.
- 여러 입력(HDMI, DP, VGA 등) 수신과 선택
- 입력 해상도를 패널 해상도로 **스케일링**, 프레임 레이트 변환
- 화질 처리: 밝기, 명암, 감마, 색온도, 선명도
- **OSD 메뉴** 합성
- 패널 인터페이스(LVDS, eDP, V-by-One) 출력
- 내장 MCU로 키 입력, 전원 관리, EDID/DDC/CI 처리

대표 제조사: Realtek, MediaTek(MStar), Novatek. 펌웨어는 보통 제조사 SDK를 기반으로 제품에 맞게 커스터마이징한다.

### 27. "화면이 가끔 깜빡인다" 불량 분석
1. **재현 조건 파악**: 특정 입력 소스/해상도/주사율, 특정 소스 기기나 케이블, 밝기 설정, 온도, 동작 시간, 발생 빈도
2. **범위 좁히기**: 다른 PC·케이블로 교체, 다른 모니터 샘플에서도 발생하는지(설계 문제 vs 개별 불량)
3. **신호 쪽 확인**: 스케일러의 신호 감지 로그 확인. 신호가 끊겼다 다시 잡히는지(케이블 품질, HPD 떨림, EDID 재읽기, HDCP 재인증)
4. **백라이트 쪽 확인**: 오실로스코프로 PWM 신호와 백라이트 전원 측정. 특정 밝기에서만 발생하면 PWM 설정 문제 가능성
5. **전원 확인**: 패널 전원 드롭, 전원부 리플
6. **펌웨어 확인**: 워치독 리셋이나 예기치 않은 재부팅 로그, 모드 변경 로직 버그, 최근 펌웨어 변경 이력 비교
7. **수정 후 검증**: 원인 수정 → 장시간 에이징 테스트로 재발 없는지 확인 → 원인과 대책을 문서화

> 포인트: 정답보다 **체계적으로 범위를 좁혀가는 과정**과 **측정 장비를 활용하는 태도**를 보여주는 것이 중요하다.
